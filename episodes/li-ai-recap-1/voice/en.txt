Building a support assistant? First, you write the prompt.
You add retrieval, so it answers from your real help articles.
You give it tools, like a function that looks up an order.
You write evals, so a change doesn't quietly break old answers.
And you run it in production: cost, speed, errors and safety.
As a stack: the model at the bottom, and the context you send it.
Retrieval adds the right documents. Tools let it ask your code to act.
Evals check the whole stack. Production keeps it fast, cheap, safe.
Why this stack? Because the model only sees what is in the request.
It has never seen your private docs, or today's orders.
Retrieval and tools pull those facts into the request, every call.
Ask a model the same question twice, and the wording can change.
So you test with evals: real questions, with checks on each answer.
Run them after every prompt or model change, to catch regressions.
Now zoom into one API call. Everything above is built on it.
You send instructions, plus messages: past turns and the question.
Plus settings, like which model to use and a maximum output length.
First, your text is split into tokens: words or pieces of words.
Each token becomes a number. The model only ever sees numbers.
In English, a token is roughly three quarters of a word, on average.
Then the model predicts the next token. Just one.
That token is added to the input, then it predicts the next one.
It stops at an end-of-reply token, or when it hits your length limit.
Streaming sends the reply piece by piece; without it, all at once.
The response also reports usage: input tokens and output tokens.

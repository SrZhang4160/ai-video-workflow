Now we're in grading. Once tasks run, who grades them?
The program that decides pass or fail is a grader.
There are a few kinds. A person can grade,
a language model can, or code can check directly.
Today we start with the simplest kind, code.
My advice is, if code can check it, use code.
Why? Let's compare the three.
A person needs minutes for every run,
and people judge differently, even day to day.
A model judge costs money, and it can be wrong too.
Code always gives the same result the same verdict,
costs almost nothing, and runs the whole set in seconds.
Take the task "My headphones broke, I want a refund."
It runs in a sandbox on a mock order database,
reset to the same state before every run.
After the run, the grader queries that database
to see if a refund record was created.
Then it checks the amount equals the order price,
since too little hurts the customer, and too much the shop.
Both check the final state, meaning the outcome.
The outcome alone isn't enough; check how it got there.
The grader reads the tool-call log for three things.
One is order. The lookup must come before the refund,
or it can't verify the order is theirs.
Another is parameters. Is the refund on the right order?
One wrong digit refunds someone else's order.
The most important is whether it overstepped its authority.
Any refund over five hundred dollars needs an approval first.
Refund without approval, and the task fails outright.
One caution, though. Don't hard-code every step.
Looking up the order twice isn't wrong.
But fixed steps would mark that correct run as failing.
So check only what must hold, and leave the rest open.
And code can't check everything, like the reply email.
It can check it was sent to the right person,
but not whether it's clear or polite.
Open-ended replies like this go to a model judge.
So it all comes down to one sentence.
If code can check it, let code check it.
It's cheap, stable, and gives the same verdict every time.
But how should a model judge the email?

If code can grade it, don't hand it to a person or a model.
The program that decides pass or fail is a grader.
A person takes minutes per task, and their standard shifts.
A model costs money, and it can be wrong.
Code gives the same result the same verdict every time,
runs the whole set in seconds, almost for free.
Headphones broke, and a customer asks a refund agent for five ninety-nine.
The task runs in a sandbox, a fake order database,
reset before every run, so runs can be compared.
First check the outcome: is there a refund record,
and is it exactly five ninety-nine? Too much or too little fails.
Then check its call log,
which lists every tool it called and the arguments.
Look up the order before refunding, or money goes out unverified.
The order number must match. One wrong digit refunds a stranger.
Then authority: over five hundred dollars needs approval first,
so refunding this five ninety-nine without approval fails outright.
But don't hard-code steps. Looking up the order twice
isn't wrong, yet fixed steps would fail it.
So check only what must hold, and leave the rest open.
Code can check the reply email was sent,
but politeness has no fixed answer, so that goes to a model.
Asked in an interview how to design graders? Say:
Code checks the outcome and the call log first.
Check only what must hold; don't fix the steps.
Only what has no fixed answer goes to a model.
First step at work: take your most important task
and write three assertions, checks code can call true or false,
like, amount equals five ninety-nine.

在 agent 开发的过程中，其实每一个 pull request 都可能悄悄地让产品变差。
比如有人改了一行 prompt，测试全过，回答质量却掉了。
我们想在合并之前就发现类似的 regression，而且每一个 commit 都要查。
但是我们又不想每一次都把全部测试跑一遍，所以我们做了一个 GitHub App，专门干这个事。
这期讲这个 GitHub App 做什么、用户看到什么，以及架构里的每一块是怎么选的。
下一期我会讲怎么让这个 GitHub App 更加可靠。
首先，这个 GitHub App 的目标很简单。
pull request 每来一个新 commit，我们就在这个 commit 上跑一遍评测。
评测就是一组测试题，用来看产品的回答有没有变差。
但如果每个 commit 都把整个测试集跑一遍，太慢，token 也烧得太多。
所以我们做了智能选取：只挑这个 commit 可能影响到的测试来跑。
这样照样能拦住把原来好好的功能改坏的情况。
同时，每个 commit 跑测试的时间省了，用户的 token 也省了。
结果显示成 commit 旁边的一个 GitHub check，就是那个绿勾或红叉。
要做到这点，每来一个 commit，GitHub 都得通知我们，我们还得有权限把结果写回去。
一种办法是个人访问令牌，也就是 personal access token。
但 personal access token 代表的是某一个人，拥有这个人的全部权限，而且常常永不过期。
这个人一离职，整个功能就断了。
GitHub App 就是为这种场景设计的。
每个 commit 都会给它发事件，它有自己的身份，只拿你申请的权限，
而且它的令牌一小时就过期。
就算泄露了，能被利用的时间也很短。
从用户这边看，只需要点几下。
第一步，登录我们的 dashboard，点 Connect GitHub。
第二步，跳到 GitHub，选要接入的仓库，点安装。
第三步，授权。这一步是向我们证明：这次安装真的是他本人做的。
之后，他们照常写代码、开 pull request。
每个新 commit 都会自动出现一个 check，点进去能看到详细结果。
这几下点击背后，是四个部分。
第一，API 服务：接收 GitHub 发来的 webhook，也负责登录。
第二，Postgres 数据库：记下每一次安装、每一次评测。
第三，工作流引擎：为每次评测开一个隔离的 sandbox，在里面跑代码。
第四，结果回到 API 服务，由它去更新 GitHub 上的 check。
串起来就是：commit 来了，存下来，跑评测，把结果写回去。
每一块，都是一个真正的选择。
每一块，我们都问同样四个问题。
第一，它适不适合这件事？
第二，运行和维护，要花多少钱、多少人力？
第三，以后想换掉，难不难？
第四，团队是不是已经会用？
最后这一条，比大家愿意承认的更重要。
先说 API 框架，也就是用什么来写这个接收 webhook 的服务。
我们的主后端是 Django，最省事的做法是直接加进去。
Django 的长处是开箱就有管理后台、数据库层和用户系统。
但这个服务很小，主要就是收 webhook。
而且要校验 GitHub 的签名，必须拿到请求最原始的内容，一个字节都不能变。
很多框架会先帮你把内容解析掉，这时再验签名，就对不上了。
Express 是最常见的选择，但输入校验要自己拼。
NestJS 适合想要严格结构的大团队。
Go 适合最看重速度的服务。
我们选了 Fastify 加 TypeScript。
输入校验是内置的，原始内容也很容易拿到，
类型检查还能在上线前就抓到很多错误。
代价是：谁能看什么的权限逻辑，都写在 Django 里，
所以这个新服务，得自己再做一遍权限检查。
接下来就是登录方案。
自己做登录，只有在身份认证就是你的产品时才划算。
因为存密码、重置密码、两步验证，以后全都得你自己维护。
如果你已经在用 Firebase 或 Supabase，就用它们自带的登录。
整套都在 AWS 上的团队，用 Cognito。
想一天之内就有漂亮的登录界面，可以用 Clerk。
最后我们选择了 Auth0。
它支持 Google 登录、按公司分组织，发的令牌里还能带权限，我们自己一个密码都不用存。
代价是：用户越多，账单越高，以后想换也要花不少功夫。
我们在这里设计了一条规则。
Auth0 只负责回答：你是谁。
你能看什么，记在我们自己的数据库里。
这样哪天即使换掉了 Auth0，权限数据一点都不用搬。
接下来，服务放在哪儿跑。
最便宜的是自己租一台虚拟机，
但系统补丁、数据备份，都得有人自己管。
Kubernetes 很强大，但得有专门的平台团队维护才划算。
Render 和 Railway 最适合小团队，
把代码推上去，它自动帮你构建、上线。
我们选了 Render。
代码合进 main branch 的时候，check 全部通过，才会自动部署，
所有配置都写在仓库里的一个文件里。
不过要注意：服务可以多开几个副本，挂一个还有别的顶上，
但它们连的都是同一个数据库，数据库一挂，全都用不了。
所以数据库的可靠性，要单独考虑。
最有意思的选择，是长任务怎么跑。
一次评测要跑好几分钟，
但 GitHub 要求 webhook 十秒内就得回复，不然就算失败。
所以收到 webhook，只能先记下来、马上回复，评测放到别处慢慢跑。
这就需要一个队列：一边往里放任务，另一边有程序把任务取出来执行。
我们最早的原型，先把这次评测存进 Postgres，再往 Redis 队列里推一个任务。
快，熟悉，大部分时候也没问题。
但这是两次分开的写入。
如果程序正好在两次写入之间崩了，
数据库里有这条评测，队列里却没有任务，永远没人去跑它。
一个解法是直接把 Postgres 当队列用，一次写入就搞定。
这适合简单的短任务。
我们的任务不简单：要等 sandbox 启动，会超时，还要重试。
所以我们选了 Temporal，一个工作流引擎。
它会记住每个任务走到了哪一步，程序崩了重启，也能接着往下跑。
Postgres 依然是唯一的事实来源，Temporal 保证每一条存下来的评测都能跑完。
代价是多维护一个系统。
对我们来说，一条评测都不丢，值得。
最后一个选择：代码在哪儿跑。
评测要运行 pull request 里的代码，而这些代码，我们不能信任。
它可能有 bug，甚至有可能故意去读别人的数据，
所以要放进 sandbox，也就是一个用完即销毁的隔离环境。
自己搭容器，控制力虽然最强，但隔离和清理都得自己负责。
E2B 和 Daytona，是专门给运行代码的 AI agent 做的。
Modal 适合这种一阵一阵跑的 Python 任务，按秒计费。
这里的教训是：光看定价页，是比较不出来哪个 tech stack 更适合的。
要拿同一个评测，在每家都跑一遍，
量一量启动要多久、超时怎么处理、清理干不干净，还有最后实际花了多少钱。
先试用 Modal，因为我们的评测是用 Python 写的，而且每次跑的时间都不长。
总而言之，每个选择都有它的好处和坏处，我们只需要选择最适合我们的那一个。
在下一期，我会讲怎么让这个 GitHub App 变得可靠，比如说：
重复的 webhook、丢失的消息、重试和重跑的区别，还有怎么公平地比较结果。
换成你，哪个选择会做得不一样？

每个 pull request，都可能悄悄让你的产品变差。
我们想在合并之前就发现它，而且每个 commit 都查。
所以我们做了一个 GitHub App，专门干这件事。
这期视频，我会讲它做什么、用户看到什么，
以及架构里每一块我们是怎么选的。
第二期，我们再讲怎么让它可靠。
目标很简单。
一个 pull request 来了新的 commit，
我们就在这个 commit 上跑评测，
再把结果作为 GitHub check 显示在 commit 上。
所以每来一个 commit，GitHub 都得通知我们。
用 personal access token 也能做到，
但它代表的是一个人，带着这个人的全部权限，
而且经常永不过期。
GitHub App 就是为这种场景设计的。
每个 commit 它都会收到事件，
它有自己的身份，只拿你申请的权限，
token 一小时就过期。
对用户来说，就是点几下。
登录我们的 dashboard，点 Connect GitHub，
选仓库，然后授权，
授权能证明这个安装确实是他自己的。
之后照常写代码就行，
每个新 commit 都会有一个 check，点进去能看详情。
这几下点击背后，是四个部分。
一个 API 服务，接收 GitHub 的 webhook，也负责登录。
Postgres 存每一个安装、每一次 run。
一个 workflow 引擎，在隔离的 sandbox 里启动每次 run。
结果再回到 API，由它更新 check。
每一部分，都是一个真正的决策。
每一个，我们都问同样几个问题。
适不适合这个活？运行和维护要花多少？
以后想换掉有多难？团队熟不熟？
最后这条，比大家愿意承认的重要得多。
先说 API 框架。
我们的主后端是 Django，
所以最顺手的做法，是直接加到 Django 里。
Django 很适合要 admin 后台、数据库层、
用户系统开箱即用的场景。
但这个服务很小，主要就是收 webhook，
而且它要拿到每个请求的原始字节，
才能校验 GitHub 的签名。
Express 是这类场景的常见默认选择，
但校验得自己拼。
NestJS 适合想要严格结构的大团队，
Go 适合最看重性能的服务。
我们选了 Fastify 加 TypeScript。
自带校验，原始 body 很好拿，
严格类型能在上线前抓住错误。
代价是：我们的权限逻辑在 Django 里，
所以这个服务得自己做权限检查。
接下来，登录。
自己做登录，只有身份本身就是你的产品时才值得，
因为密码、重置、两步验证，从此都归你管。
本来就用 Firebase 或 Supabase 的，用它们的 Auth 就好。
Cognito 适合全在 AWS 上的团队。
Clerk 适合想一天就做出漂亮登录页的情况。
我们选了 Auth0，因为要 Google 登录、组织，
还有带权限的 token，而且永远不用存密码。
代价是账单随用户增长，
以后想换掉也要花真功夫。
所以我们守一条规则：Auth0 只告诉我们这个人是谁。
他能看什么，存在我们自己的数据库里。
这样退路一直都在。
然后，跑在哪儿。
一台普通虚拟机最便宜，
前提是有人愿意打补丁、做备份。
已经有平台团队的话，Kubernetes 才划算。
Render 和 Railway 适合小团队，
推代码就能跑。
我们选了 Render。
只有 check 全过了，才会从 main 部署，
整套配置就在仓库里的一个文件里。
不过要注意：应用多开几份，
数据库并不会因此更可用。
这个要单独规划。
最有意思的决策，是长任务怎么跑。
一次评测要好几分钟，
但 GitHub 要求 webhook 十秒内回复，
所以活得放到别处去干。
我们第一版原型，先把 run 存进 Postgres，
再往 Redis 里推一个任务。
快、熟悉，大多数时候也没问题。
但这是两次独立的写入。
如果进程刚好在中间崩了，
run 存在，却永远没人去处理。
直接用 Postgres 当队列能解决这个问题，
也很适合短小简单的任务。
可我们的任务不简单。
要等 sandbox，会超时，还要重试。
所以我们选了 Temporal。
Postgres 仍然是唯一的事实来源，
Temporal 保证每个存下来的 run 都真正跑完。
代价是多维护一个系统。
对我们来说，永远不丢 run，值得。
最后一个决策：代码在哪儿跑。
Pull request 里的代码不可信，必须进 sandbox。
要完全掌控，就用自己的容器，
但隔离和清理都得自己负责。
E2B 和 Daytona 是给跑代码的 AI agent 做的。
Modal 适合短时爆发的 Python 任务，
按秒计费。
经验是：别看定价页来比较。
在每家跑同一个评测，测冷启动、
超时、清理，还有真实花费。
我们先拿 Modal 试用，
因为我们的评测器是 Python 写的，每次 run 都很短。
所以每个选择都有代价，
我们选的是自己承受得起的那个。
第二期，我们讲怎么让它可靠：
重复的 webhook、丢失的消息、重试和重跑的区别，
还有公平的比较。

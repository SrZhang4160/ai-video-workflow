A pull-request check sounds simple. Making it reliable is not.
We built a GitHub App that runs our evaluations on every new commit,
and reports each result on that commit, for every team using it.
Let's cover the concept, the design, and the failures to plan for.
First, the concept. A GitHub App is a bot with its own identity.
An organization installs it on the repositories it chooses,
and grants it only the permissions it requests.
Why not simply use a personal access token? Because it acts as you.
An app receives short-lived tokens, valid for about an hour,
limited to a single installation. GitHub also sends it events,
such as a new pull request, which is exactly the trigger we need.
Now, the design. GitHub notifies our service through a webhook.
The service records the event in a database,
and hands the actual work to a separate runner.
The runner reports its progress and, finally, the result.
The service posts it as a check. Next, let's walk through each step.
The first step is registering the app with GitHub.
We provide a webhook URL and choose its permissions.
We keep them minimal: write checks, read code, read pull requests.
The app can never modify code. Next, a team installs it.
When a team installs the app, we must link it to the right customer.
However, the installation ID in the setup URL can be forged.
So we ask the user to sign in with GitHub,
and verify that they actually have access to that installation.
After that, every new commit triggers a webhook. First, we verify it:
we check the signature on the raw bytes, before parsing anything.
GitHub may deliver the same event more than once,
so we record each delivery ID and ignore duplicates.
We store the event and respond within ten seconds,
and the slower work continues in the background.
The runner then evaluates the exact commit, not the branch name,
because a branch can move while the job is still running.
Fork pull requests carry untrusted code, so we skip them: safety first.
And the app's private key stays in our backend, never in the runner.
That covers the normal path. Now, what happens when something fails?
First, crashes. We save each run before handing it off,
and submit it with an idempotency key,
so if a response is lost and we retry, no second job is started.
After a crash, a reconciler resumes any unfinished runs.
We also store results separately from reporting,
so a failed call to GitHub cannot erase a result.
Second, messages can arrive late or out of order.
Every update carries an attempt ID and an increasing sequence number.
We accept only the current attempt, and only newer numbers,
so an old result can never overwrite a newer one.
The check follows the same rule: it is tagged with the run ID,
and we search the commit for it before creating another.
Third, a retry and a rerun are different things.
A retry simply continues the same run after a lost request.
A rerun is a new measurement, so the earlier result is kept.
When our infrastructure fails, we report that, not a code failure.
And when we compare results, we compare like with like:
the same test version, model settings, and runtime.
A missing score is recorded as missing, never as zero.
These requirements shaped our stack. The service is TypeScript on Node.
Everything is JSON, and types catch payloads with the wrong shape.
We chose Fastify because it gives direct access to the raw body,
which signature checks require, and it validates schemas quickly.
Zod validates every external input, from GitHub or the runner,
before we rely on it.
For storage, PostgreSQL holds all of the state.
Transactions keep each run and its status consistent.
Unique keys prevent duplicate runs.
Locks ensure that only one worker reports a given run.
We chose not to add a separate queue yet.
Postgres covers it at our scale, with one fewer system to fail.
The runner is a separate service,
because it executes untrusted code and scales independently.
In tests, an in-memory Postgres keeps the suite fast,
and CI runs against a real Postgres to test real database behavior.
The same principles apply beyond GitHub. Consider a Slack alert
that fires when an account reaches ninety percent of its weekly usage.
We record the alert once per account per week in our own database,
and only then send it.
There is exactly one sender, so nobody receives it twice.
And the threshold is computed in the same window we enforce,
not in an analytics tool that uses a different time zone.
To summarize: tie every run to a single commit.
Make every step safe to repeat.
Reject stale attempts, and classify every failure clearly.
And keep missing data missing.

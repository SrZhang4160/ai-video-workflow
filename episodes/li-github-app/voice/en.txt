We needed a trigger: whenever a pull request gets a new commit,
our evaluations should run against that exact commit,
and the result should appear on the commit, for every team using it.
The natural way to get that trigger is a GitHub App.
A GitHub App is a bot with its own identity.
A team installs it only on the repositories they choose,
and it gets only the permissions it needs, such as writing checks.
A personal token cannot do this well, because it acts as you.
The app instead gets short-lived tokens, valid for about an hour,
for one installation only. More importantly, GitHub sends it events,
like a new commit on a pull request. That is our trigger.
Here is the flow. A new commit makes GitHub send our service a webhook.
The service saves it in a database,
which then triggers a job on a separate runner.
The runner reports progress, and finally the result,
which the service posts back to the commit as a check.
Before any of that, a team installs the app, and we link it to them.
One subtlety: the installation ID in the setup URL can be forged.
So the user signs in with GitHub,
and we confirm they really have access to that installation.
Now the first step. When a webhook arrives, we verify its signature,
computed over the raw bytes, before we parse anything.
GitHub may deliver the same event more than once,
so we record each delivery ID and drop the repeats.
Then we store it and reply within ten seconds,
leaving the slow work for the background.
That step drove our first stack choice: TypeScript on Node.
Webhooks are JSON, and types catch payloads with the wrong shape.
For the server we chose Fastify, because it exposes the raw body,
which the signature check needs, and it validates schemas quickly.
And zod validates every external input, from GitHub or the runner,
before we rely on it.
The next step is saving the run, and for that we chose PostgreSQL.
A transaction stores the run and its status together.
A unique key on the commit and test version stops duplicate runs.
And locks make sure only one worker reports a given run.
We decided not to add a separate queue yet,
because at our scale, Postgres can serve as the queue, too.
Saving the run triggers the job. The runner gets the exact commit,
not a branch name, because a branch can move during the run.
Fork pull requests carry untrusted code, so we skip them.
And the app's private key stays in our backend, never in the runner.
That is also why the runner is its own service:
it executes untrusted code, and it scales independently.
To test all of this, an in-memory Postgres keeps the tests fast,
and CI runs a real Postgres, so database behavior is really tested.
But a handoff can fail. What if the runner's reply is lost?
Because the run was saved first, nothing is forgotten.
We resend it with the same idempotency key,
so the runner recognizes it, and no second job is started.
If our service itself crashes, a reconciler resumes unfinished runs.
And results are stored separately from reporting,
so a failed call to GitHub cannot erase a result.
Then the runner reports back. Messages can arrive late or out of order,
so each one carries an attempt ID and an increasing sequence number.
We accept only the current attempt, and only newer numbers,
so an old result can never overwrite a newer one.
Finally, the check on GitHub is tagged with the run ID,
and we look for it before creating another, to avoid duplicates.
Across all of these steps, we keep retries and reruns apart.
A retry continues the same run after a lost request.
A rerun is a new measurement, so the earlier result is kept.
If our infrastructure fails, we say so, rather than fail the code.
And when we compare results, we compare like with like:
the same test version, model settings, and runtime.
A missing score stays missing; it is never a zero.
The same principles apply beyond GitHub. Consider a Slack alert
that fires when an account reaches ninety percent of its weekly usage.
We record the alert once per account per week in our own database,
and only then send it.
There is exactly one sender, so nobody receives it twice.
And the threshold is computed in the same window we enforce,
not in an analytics tool that uses a different time zone.
To summarize: tie every run to a single commit.
Make every step safe to repeat.
Reject stale attempts, and classify every failure clearly.
And keep missing data missing.

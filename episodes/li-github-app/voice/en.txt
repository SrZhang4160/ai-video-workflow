How to build a GitHub App that evaluates every pull request.
We'll start with what it does, and how a user experiences it,
then the architecture choices and their trade-offs,
and in part two, the details that make it reliable.
For this GitHub App, our goal was simple to state.
Whenever a pull request gets a new commit,
we want to run our evaluations against that exact commit,
to detect any potential regression,
and show that result on the commit as a GitHub check.
We use a GitHub App here,
because GitHub sends it an event for every commit.
And unlike a personal token, it has its own identity,
narrow permissions, and short-lived tokens
for each installation of the GitHub App.
From the user's side, it takes a few clicks.
They sign in to our dashboard, and click "Connect GitHub".
Then they install the app on the repositories they choose.
GitHub asks them to authorize, which proves they own that install.
After that, they simply open pull requests.
A check appears on each commit: queued, running, then a result,
with a link to the full results in our dashboard.
Behind that, there are four parts.
An API service receives GitHub's webhooks and the user's sign-in.
Postgres stores every installation, delivery and run.
A durable workflow hands each run into an isolated sandbox.
Results flow back to the API, which posts the check.
We chose our tech stack based on the following considerations.
Every part of this architecture was a decision, with real options.
We judged every option with the same questions.
Does it fit the job? What does it cost to run, and to operate?
How locked in would we be? And does the team already know it?
Let's go through the decisions one at a time.
First, the API framework. The common options:
Express: minimal and everywhere, but you add validation yourself.
Fastify: fast, with schema validation built in, but less opinionated.
NestJS: strong structure for large teams, at the cost of boilerplate.
Django: batteries included, with admin and auth, but heavier.
FastAPI: async Python, with automatic validation and docs.
Go: very fast and lean, but more code for the same JSON handling.
We chose Fastify with TypeScript. The service is small and focused,
it needs the raw body for signatures, and strict types catch bugs in CI.
The cost: we couldn't reuse our existing Django permission code.
Next, sign-in. You can build it yourself, or use a provider.
Building it gives full control, but you own passwords, resets and M F A.
Auth0: mature, with social login, organizations and permissions.
But its price grows with users, and moving away later is work.
Clerk: excellent developer experience and ready-made UI.
Amazon Cognito: cheap at scale and AWS-native, but harder to use.
Firebase or Supabase Auth: simple and cheap, tied to their platforms.
We chose Auth0: Google login, plus signed tokens with permissions,
and we never store a password. It tells us who someone is;
what they may access still lives in our own database.
Then, where the service runs.
A plain VM is cheapest, but patching, backups and deploys are on you.
Kubernetes on a big cloud scales to anything, with heavy operations.
Render deploys from Git, with health checks and managed databases.
Railway is similar, very quick to start, with usage-based pricing.
Managed platforms cost more per unit, and give you less control.
We chose Render: it deploys from main only when checks pass,
the setup lives in the repo, and a small team doesn't run servers.
One caveat: more app copies don't make the database highly available.
Evaluations take minutes. So how do you run long jobs?
In the webhook handler: simplest, but GitHub expects a reply in ten seconds.
Postgres plus a Redis queue: fast and familiar,
but saving and queueing are two writes, so a crash can lose work.
Postgres alone as the queue: one system, transactional, fewer features.
A workflow engine like Temporal: retries and recovery built in,
but one more system to run, and new rules to learn.
Our prototype used Redis, and it showed exactly that gap.
So Postgres is the source of truth, and Temporal runs the work.
Pull-request code is untrusted. So where does it run?
Our own containers: full control, but isolation and cleanup are ours.
E2B: microVM sandboxes built for AI agents that run code.
Daytona: fast sandboxes for AI-written code, with lasting workspaces.
Modal: Python-first serverless containers, billed per second.
Price lists don't compare them fairly.
Run the same pinned evaluation on each, and measure cold start,
timeouts, cleanup and the real bill.
We started with Modal: our evaluators are Python, and runs are short.
So those are the choices: options, trade-offs, and a reason for each.

An eval is a set of test cases plus grading rules.
Grading a single model call isn't that hard.
With our refund agent, it's much harder.
Why? Let's put the two side by side.
Start with a single model call, say a classifier.
We ask if a message is a refund request,
like "My headphones broke last week. Refund, please."
The model says yes, and so does the answer key.
Compare the two, and you're done in one step.
Here, the grader is one line of code.
With an agent, three things get harder.
The first is that it takes many steps, not just one.
It looks up the order, checks who bought it,
checks the date and amount, then refunds,
and finally emails the customer.
Any step can go wrong, and a mistake carries forward.
If it grabs the wrong order, every later step is wrong.
Or say it skips the buyer check and refunds anyway,
while the final email still sounds polite.
Judge only that last message, and you'll never see it.
The second is that it acts, and changes real data.
A plain model call only produces text.
But when it calls the refund tool, real money goes out.
A change to outside data is called a side effect.
A reply can be rewritten; a refund can't be taken back.
So grading has to check the database, not just the reply:
is there a refund record, and is the amount right?
And tests can't move real money, so they run in a sandbox.
A sandbox is an isolated setup you reset after each run.
The third is that it can take a different path each run.
Model output is random, so for the same message,
it may look up the order, or ask for the number first.
It's mostly right, but now and then it skips the check.
So passing once doesn't mean passing every time.
Run each case several times to see if it's stable.
Many steps, side effects, a different path each run:
a single model call has none of these.
So this episode comes down to one point:
the final reply alone is nowhere near enough.
Should you grade the end result, or every step?
That's what we'll look at in the next episode.

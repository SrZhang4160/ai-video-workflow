First, the block at the front: the entry.
When the user clicks in the dashboard,
the request goes to a Cloudflare Worker.
A Worker is a small piece of code that runs on Cloudflare's network.
It's the only way into the playground.
The service itself is not public.
Anyone who tries to reach it directly gets turned away.
So how does the Worker get in? It calls the service with its own identity.
That identity has one permission, calling this service, and nothing else.
So even if something goes wrong with it, it can't do much.
The Worker also cleans each request first.
Any "who I am" information that came in from outside, it deletes,
because anything from outside could be forged.
The service only trusts an identity the Worker has confirmed.
And the internal reconcile endpoint can't be called from outside at all.
Each session also gets its own subdomain,
and the entry routes it to the right session.
Why each session needs its own subdomain, I'll explain when we get to robustness.
Next in line is the playground service.
The easiest option was to put all this logic into our main backend. I didn't.
For one, the editor stays connected to the service over a WebSocket,
a two-way connection that stays open for a long time.
The main backend handles short request-and-response calls.
They're very different.
For another, its traffic rises and falls on a different schedule from the main product,
so it has to scale on its own.
Most important, if it breaks, it mustn't take the main product down with it.
So I made it a separate small service,
written in TypeScript with the Hono framework, deployed on Google Cloud Run.
You give Cloud Run a container, and it runs and scales it,
so I don't manage any machines.
The trade-off: it can't reuse the backend's permission code,
so every time, it has to ask the backend: is this user allowed?

To change anything, Terraform first makes a plan that shows exactly what will change,

Staging and production each have their own copy, kept apart.
Now the secrets. Our service needs two keys:
one for calling E two B, and one for reaching our backend.
Neither key can go in the code or in Terraform,
because both live in the repo, and anyone who can read the repo would see the keys.
So the keys live in Google Secret Manager.
Terraform only records each key's name and version.
When the service starts, Cloud Run fetches the keys and hands them to it.
And only the service's own account is allowed to read them.

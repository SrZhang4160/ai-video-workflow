这一期讲每一块的技术栈是怎么选的。
我们先把需求理清楚。
功能上，点一下就要打开一个真正的编辑器，马上能用。
用户的代码要能真的跑起来，包括 Docker，
因为每一个 agent 测试，都跑在它自己的容器里。
用户离开以后，我们启动的所有东西都要清理掉。
然后是非功能需求。
隔离要强，因为是陌生人在跑我们从没见过的代码。
启动要快，因为点完等太久，用户就走了。
没人用的时候成本要低，因为大部分时间都没人在用。
还有，真正的密钥绝对不能进入沙箱。
后面的每一个选择，都会回到这几条需求上，
而且每个选择都有代价。
接下来，一块一块地选。
入口的需求是：只有一个受控的进口，服务本身不公开。
Cloudflare Worker 正好能做到。
Worker 是跑在 Cloudflare 网络上的一小段代码，
服务只信任经过 Worker 确认的用户。
而且我们的域名和 dashboard 本来就在 Cloudflare 上。
代价是用了两朵云，要在两个地方配置，
出了问题还要翻两套日志。
接下来是服务。第一个问题：
是把它塞进主后端，还是单独做一个服务？
我选了单独做。因为它要长时间保持 Web Socket 连接。
它的流量起伏和主产品不一样，需要单独扩缩。
它要是出了问题，主产品必须照常运行。
代价是它没法复用后端的权限代码，
所以每次操作都要去问一下后端。
第二个问题，服务跑在哪里？
Cloud Functions 对单个请求的时长有限制，
放不下长时间的 WebSocket。
自己开虚拟机或者 Kubernetes 集群，就得自己管机器。
Cloud Run 刚好合适：我只要交给它一个容器，
它就负责运行和扩缩，也支持 WebSocket。
代价是，如果服务从零启动，第一次点击会多等几秒，
所以我一直保留一个实例在跑，没人用也要付这份钱。
另外，一个 WebSocket 连接算一个请求，
所以会话太长会被断开，编辑器要重新连接。
第三个问题是语言，我用的是 TypeScript 加 Hono。
Hono 是一个很轻的 Web 框架，类似 Express，但更小，
同一份代码既能跑在 Node 上，也能跑在 Cloudflare Workers 上。
TypeScript 也和周边的工具一致：
Worker、E2B 的 SDK，还有 VS Code。
然后是状态。服务会同时跑好几个副本，它们共享同一批会话，
而且"检查限额、再占名额"这件事，必须在一个事务里完成。
Cloud SQL 上的 Postgres，事务和查询能力都很强，
但数据库要全天开着，没人用也在花钱。
Redis 很快，但数据主要放在内存里，
不适合存放唯一的真实记录。
Firestore 支持事务，而且完全不用运维。
它按读写次数收费，所以没人用的时候几乎不花钱。
所以我选了 Firestore。
代价是查询能力比较弱，而且绑定在 Google Cloud 上。
所以我把它放在一层接口后面，本地开发时用 SQLite 实现同一个接口。
还有一点，如果每次启动都去改同一个共享计数，比如全局上限，
那在高并发时，这个文档就会成为瓶颈。
等流量到现在的十倍，我会把这个计数拆开。
到这里，需求有了，整个服务端也选好了。
下一期，我用同样的方法来选沙箱端。
用户的代码跑在哪、用户看到的是什么编辑器，以及 AI 怎么调用模型。

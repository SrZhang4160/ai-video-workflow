When you chat with an AI, it doesn't remember the last line.
Each time you speak, the app resends the whole chat from the top.
Like calling support and retelling your story every single time.
The longer the chat, the more to retell, the slower the reply starts.
Yesterday, Anthropic's Claude API added a new feature,
message threads. It's like support opening a case file for you.
The first time, you tell the whole story once.
After that, you say only the new part and give the case number.
That case number is the ID of the previous reply.
Anthropic says: on very long requests of 500K to 1M tokens,
the median wait for the first token dropped about 35%.
That's measured in Claude Code, where it's on for most users.
Why faster? Before, each turn re-uploaded and re-processed it all.
Now the chat stays on the server; mainly the new part gets processed.
But the model still reads the whole conversation each time,
so billed tokens, prices and rate limits stay the same.
The rules: a thread expires 5 minutes after its last request,
and continuing then returns a 404, so you resend it all.
It's append-only, and each reply ID can be continued once.
When streaming, wait until the reply fully ends before the next turn.
And there's no API to list, read or delete a thread.
Data: threads are encrypted in memory, never written to disk,
deleted within an hour; not eligible for ZDR or HIPAA.
And it doesn't work with batches, token counting, compaction and more.
My take: this is built for long-running agents.
Short chats save little; very long coding agents gain the most.
Keep your own copy of the chat, so you can resend it when it expires.
In one line: the chat stays on the server, you send only the new part.
Long chats reply sooner, at the same price.
Watch for when it leaves beta,
and whether an API to view and delete threads arrives.

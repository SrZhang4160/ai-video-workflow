Last time we graded one case. Today we look at the whole set.
Eval cases can serve very different purposes.
Some check whether it can learn something new.
Others check it can still do what it already could.
These are capability evals and regression evals.
Capability evals test what the agent can't do well yet.
Say a customer buys three items and returns one.
The refund has to cover only that item.
If that item is over five hundred dollars, it also needs approval first.
Today's version gets most of these wrong.
The pass rate is the share of cases it gets right.
A low rate is normal, since the cases are hard on purpose.
What you watch is whether it rises after each change.
If every case passes, the set is too easy; add harder ones.
Regression evals test what it already does well.
Like the headphones bought seven days ago, for three hundred dollars.
These already pass, and they should keep passing.
A regression is when what used to work now fails.
It usually comes from changing something else.
Say you edit the prompt to handle single-item returns,
and now it stops asking for approval over five hundred dollars.
Run the regression evals, and that old case now fails.
So run them on every change, and don't let one drop.
If even one fails, fix it before you ship.
Side by side, the difference is clear.
Capability evals start low, and you watch them rise.
Regression evals sit near a hundred percent, and you watch for drops.
So keep the two sets, and their scores, separate.
If you mix them into one pass rate,
two hard cases start passing while two old ones fail,
the total doesn't move, and the problem stays hidden.
So do capability cases stay there forever?
No. Once single-item returns pass reliably,
they move into the regression set, and must never fail again.
So the regression set grows, and the floor keeps rising.
So this episode comes down to one idea:
capability evals push upward; regression evals hold the floor.
One tests what it can't do yet; the other guards what it can.
Both sets should come from your own real cases.
So why not just test it on public benchmarks?

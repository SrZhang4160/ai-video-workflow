上一期，我们设计了一个 GitHub App，给每个 pull request 做评测。
webhook 到了，我们存下一次评测，
sandbox 跑测试，结果作为 check 回到 commit 上。
这是一切顺利的情况。
这期讲的，是所有可能出错的地方。
先说一切的起点：webhook。
我们要在每个新 commit 上跑评测，所以得第一时间知道有新 commit。
webhook，就是 GitHub 主动通知我们的方式。
我们事先给 GitHub 登记一个网址，这就是 webhook 地址。
每次有人往 pull request 推 commit，GitHub 就往这个地址发一个请求，
里面写着是哪个仓库、哪个 pull request、哪个 commit。
问题是，这个地址是公开的，谁都能往里发请求。
所以收到请求，第一件事是校验 GitHub 的签名。
创建 app 的时候，我们和 GitHub 约定了一个密钥，叫 webhook secret，只有我们双方知道。
GitHub 每发一条消息，都会用这个密钥，根据消息内容算出一个签名，跟消息一起发过来。
我们收到后，用同一个密钥，对收到的内容再算一遍。
两个签名一样，说明消息确实是 GitHub 发的，路上也没被改过。
不一样，直接拒绝。
但签名只能证明：这条消息来自 GitHub。
它不能证明，这个仓库属于我们哪个客户，这个客户又有没有权限用它。
所以还有第二道检查。
每条消息里都带着一个 installation ID，也就是 app 这次安装的编号。
我们去自己的数据库里查：这个编号绑定在哪个客户账号上？这个仓库，是不是这个客户开启了的？
两样都对得上，才继续处理；对不上，就忽略这条消息。
那这个绑定是怎么建立的？后面细讲。
还有一个问题：同一个事件，GitHub 可能发两次。
比如一次投递失败后被重新发送，同一条消息就会再来一遍。
如果每次都照单全收，同一个 commit 就会被评测两次。
好在每条消息都有一个编号，叫 delivery ID，重发的时候，编号不变。
所以每次收到一条消息，我们会先查：这个 delivery ID 见过没有？
见过，说明是重复的，我们把它直接忽略。
没见过，就把这个 ID 存下来，再把事件存进数据库。
存好之后，我们马上回复 GitHub：收到了。真正的评测，交给后台去跑。
这样，回复够快，同一个事件也只会处理一次。
刚才说的绑定，是在安装的时候建立的，这也是最容易出错的地方。
流程是这样的：用户在我们的 dashboard 点 Connect GitHub，跳到 GitHub 去安装 app。
装完以后，GitHub 会让用户的浏览器跳回我们的网站。
跳回来的网址末尾，带着一个 installation ID，也就是 GitHub 给这次安装的编号。
我们要做的，就是把这个编号，记到当前登录的客户账号下面。
问题在于，这个网址是在用户自己的浏览器里打开的。
用户可以把网址里的编号改成任何数字，再打开一次。
如果他填的是别的公司的安装编号，而我们照单全收，
那家公司的仓库就绑到了他的账号上，他就能看到人家的评测结果。
所以，网址里的编号，只代表用户声称自己装了哪个。我们必须自己核实。
核实分两步。
第一步：用户点 Connect GitHub 的那一刻，我们生成一个一次性链接，并记下是哪个账号发起的。
这个链接只能用一次，十分钟后自动失效。
用户从 GitHub 回来时，必须带着这个链接。
这样我们才知道：是刚才那个账号发起的这次安装，不是旧链接，也不是伪造的请求。
第二步：让用户在 GitHub 上授权我们的 app，我们拿到一个代表这个用户的令牌。
我们拿这个令牌去问 GitHub：这个用户能访问的安装里，有没有网址里的这个编号？
GitHub 说有，我们才把这次安装绑定到账号上；说没有，就拒绝。
如果用户在这个过程中把 app 卸载了，一次性链接也会作废，什么都不会绑定。
接下来，要先定义清楚：一次评测，到底评的是什么。
对我们来说，一次评测由四样东西确定：哪个仓库、哪个 pull request、哪个 commit，以及哪个版本的评测。
这四样都一样，才算同一次评测。
首先我们要注意的点是：我们永远评测一个确切的 commit，而不是一个分支名。
因为分支名指向的是这个分支上最新的 commit，而它随时会变：测试跑到一半，可能就有人推了新代码上去。
如果我们只记分支名，得出的结果就会被当成新代码的结果，可新代码其实根本没被测过。
所以一开始就把 commit 固定下来，结果才能准确对应到真正被测的那份代码。
其次，来自 fork 的 pull request，我们直接跳过，不做评测。
fork 是别人把仓库复制到自己名下的副本，所以从 fork 发来的 pull request，里面是团队以外的人写的代码。
而评测要在我们的机器上运行这些代码。如果来者不拒，任何陌生人都能开一个 pull request，在我们的机器上跑任意代码。
所以我们只评测仓库内部成员提交的代码。
第三，app 的私钥永远只留在后端，绝不进 sandbox。
因为这把私钥能以我们 app 的身份去操作客户的仓库，而 sandbox 里跑的，恰恰是我们不信任的代码。
私钥一旦进了 sandbox，这些代码就有机会把它偷走，拿去冒充我们。
再来看网络：消息在路上可能会丢，也可能会迟到，这两种情况都要处理。
先说丢。假设我们发了一个请求去启动评测，但对方的回复在路上丢了。
这时我们没法知道评测到底启动了没有；如果直接再发一次，同一个评测就可能跑两遍。
所以我们的做法是：先把这次评测存进数据库，拿到一个唯一的 run ID，再带着这个 ID 去发请求。
这个 ID 叫幂等键。对方收到请求，先看这个 ID，见过就知道是同一件事。
所以不管请求重发几次，评测都只跑一次。
再说迟到，它是反过来的问题。
同一次评测可能有好几次尝试，如果旧的那次比新的晚结束，它的结果就会把新结果覆盖掉。
所以每次更新结果时，都带上尝试编号，和一个只增不减的序号。
我们只接受比手上更新的结果，更旧的直接忽略，这样迟到的旧结果就盖不掉新结果。
同样的道理，GitHub 上的 check 也记着 run ID，所以消息重发时，我们是去更新原来那个 check，而不是再建一个重复的。
这就引出一个常被混在一起的区别：重试和重跑。
重试，是基础设施的某一步没做成，再做一遍：比如请求没发出去就重发，check 没写上就重写。
它还是同一次评测，所以结果不会变。
重跑，是把测试本身重新执行一遍。这等于做了一次新的测量，结果可能不一样。
正因为重跑是新的测量，我们不会用重跑的结果替换第一次的结果，而是都保留下来，
并且如实标注：是一次就过，还是重跑之后才过。
这很重要。一个要跑到第三次才过的测试，并不说明代码没问题，而是说明这个测试不稳定，英文叫 flaky。
还有一种情况：失败的原因不在用户的代码，而在我们自己的基础设施，比如 sandbox 没启动起来。
这时 check 会显示需要处理，而不是失败，这次也不计分。
因为是我们自己出了故障，不该算到用户代码的头上。
然后是比较：每次评测的结果，都要和一个基准结果比，才知道这次改动是让产品变好了，还是变差了。
但这个比较要公平，前提是除了代码之外，其他条件都一样：
测试题的版本、评测程序的版本、模型的设置，还有运行环境。
只要其中一样不同，分数的变化就可能来自这个条件，而不是来自代码。
所以我们给每个结果都记下当时的配置；配置对不上的两个结果，我们拒绝比较。
缺失的数据也要小心，因为零分和缺失是两回事。
零分的意思是：这道题我们测了，它没通过。缺失的意思是：这道题我们根本没测。
用了智能选取以后，本来就只跑一部分测试，所以没跑的那些都是缺失，而不是零分。
如果把缺失当成零分去算平均分，平均分就会无缘无故往下掉，看起来像是代码变差了。
所以缺失就记为缺失，同时单独报告覆盖率，也就是这次实际测了多少。
最后，还有几个小习惯，作用很大。
第一，新功能放在一个开关后面上线，这个开关叫 feature flag。
开关关着的时候，app 只回应健康检查，别的什么都不做。
开关打开、但配置不完整的时候，它会直接拒绝启动。因为配置缺了迟早会出错，与其上线以后才出错，不如一开始就停下来。
第二，三个密钥分开存放：app 私钥、OAuth 密钥和 webhook 密钥。
这样就算泄露了一个，另外两个守着的东西依然安全。
第三，如果有人来查别的公司的评测，我们返回不存在，而不是没权限。
因为回答没权限，就等于告诉对方：这个东西确实存在。
第四，用量提醒也只发一次。
当一个账号的用量超过上限，我们会给它发一条提醒。
但后台有好几个程序同时在干活，它们可能在同一时刻都发现用量超了。如果各发各的，用户就会一下收到好几条一样的提醒。
所以发提醒之前，程序要先在数据库里登记一条记录：这个账号，这一周，已经提醒过了。
同一个账号、同一周，这条记录只能登记成功一次。登记成功的那个程序才去发提醒，其他程序发现已经登记过，就什么都不做。
这和前面处理重复 webhook 是同一个办法：先登记一个唯一的编号，再去做事。
综上所述，如果你要做类似的东西，要记住四件事。
每个输入，先验证，再相信。
每次评测，钉死在一个确切的 commit 上。
每一步，都要能安全地重复执行。
重试、重跑和缺失数据，都要如实记录。

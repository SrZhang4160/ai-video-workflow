上一期，我们设计了一个 GitHub App，给每个 pull request 做评测。
webhook 到了，我们存下一次评测，
sandbox 跑测试，结果作为 check 回到 commit 上。
这是一切顺利的情况。
这期讲的，是所有可能出错的地方。
先说一切的起点：webhook。
我们要在每个新 commit 上跑评测，所以得第一时间知道有新 commit。
webhook，就是 GitHub 主动通知我们的方式。
我们事先给 GitHub 登记一个网址，这就是 webhook 地址。
每次有人往 pull request 推 commit，GitHub 就往这个地址发一个请求，
里面写着是哪个仓库、哪个 pull request、哪个 commit。
问题是，这个地址是公开的，谁都能往里发请求。
所以收到请求，第一件事是校验 GitHub 的签名。
GitHub 会用一个只有我们双方知道的密钥，给每条消息签名。
我们用同一个密钥再算一遍，对得上，才往下处理。
但签名只能证明：这条消息确实来自 GitHub。
它不能证明，这个客户有权使用这个仓库。
这需要另一道检查：这个仓库的安装，是不是绑在这个客户的账号上。
GitHub 还可能把同一个事件发两次。
所以我们记下每个 delivery ID，重复的直接忽略，
把事件存好，马上回复。
下一个坑在安装流程里。
用户在 GitHub 上装完 app，GitHub 会把他跳回我们的网站，
网址里带着一个 installation ID，也就是这次安装的编号。
我们要靠它，把这次安装和用户的账号绑在一起。
很想直接信它，但网址谁都能改。
如果有人把编号改成别人的，就能把别人的仓库绑到自己账号上。
所以我们只把它当线索，不当证据。
第一，整个流程绑定一个一次性链接，十分钟就过期。
第二，用户在 GitHub 上授权，我们再向 GitHub 确认：这个用户真的能访问这个安装。
两条都对得上，才把安装绑到账号上。
如果中途 app 被卸载，链接也随之失效。
接下来，要定义清楚：一次评测到底是什么。
对我们来说，就是一个仓库、一个 pull request、一个 commit，加上一个评测版本。
我们永远跑确切的那个 commit，而不是分支名。
因为分支是会动的：测试还在跑，可能又有人推了新代码。
那结果描述的，就是一份没人测过的代码。
来自 fork 的 pull request，我们跳过。
fork 是别人复制出去的仓库，那是外部的代码，却要在我们的机器上跑。
还有，app 的私钥永远只留在后端，不会进到 sandbox 里。
再来看网络。
消息会丢，也会迟到。
先说丢。
假设我们发请求去启动一次评测，结果回复丢了。
到底启动了没有？我们不知道。
如果直接再发一次，可能就跑了两遍。
所以我们先把这次评测存进数据库，拿到一个 run ID，
再带着这个 ID 发请求。这个 ID，叫幂等键。
对方看到同一个 ID，就知道是同一件事，不管收到几次，都只跑一次。
迟到，是反过来的问题。
一个旧的尝试比新的晚结束，就会把新结果覆盖掉。
所以每次更新，都带一个尝试编号，和一个只会增加的序号。
比我们手上已有的更旧的，直接忽略。
GitHub 上的 check 也带着 run ID，所以我们是更新它，而不是再建一个重复的。
这就引出一个常被混在一起的区别：重试和重跑。
重试，是重复一个基础设施步骤，
比如请求没发出去，再发一次；check 没写上，再写一次。
还是同一次评测，结果不会变。
重跑，是把测试重新执行一遍，那是一次新的测量。
所以我们保留第一次的结果，并且如实标注：
是一次就过，还是重跑之后才过。
一个第三次才过的测试，不叫可靠，叫不稳定，英文叫 flaky。
还有，如果是我们自己的基础设施出了问题，
check 会显示需要处理，而不是失败，也不会打分。
我们自己宕机，不该怪到你的代码头上。
然后是比较。
每次结果都要和一个基准比，看是变好还是变差。
这个比较要公平，前提是其他条件都一样：
测试题的版本、评测程序的版本、模型的设置，还有运行环境。
所以每个结果都记下当时的配置，配置对不上，就拒绝比较。
缺失的数据也要小心。
零分的意思是：我们测了，它没通过。
缺失的意思是：我们根本没测。
用了智能选取，本来就只跑一部分测试，没跑的那些是缺失，不是零分。
如果把缺失当成零，平均分就会无缘无故往下掉。
所以缺失就记为缺失，另外单独报告覆盖率，也就是测了多少。
还有几个小习惯，作用很大。
第一，新功能藏在一个开关后面上线，这个开关叫 feature flag。
关着的时候，app 只回应健康检查。
开着但配置不全，它直接拒绝启动，而不是跑起来以后才出错。
第二，三个密钥分开存：私钥、OAuth 密钥、webhook 密钥。
这样泄露一个，不会全部失守。
第三，有人去访问别的公司的评测，我们返回不存在，而不是没权限。
因为说没权限，就等于告诉对方：这个东西是存在的。
第四，同样只做一次的思路，也用在用量提醒上：
每个账号每周只提醒一次，不管有多少个程序同时发现。
所以，如果你要做类似的东西，记住四件事。
每个输入，先验证，再相信。
每次评测，钉死在一个确切的 commit 上。
每一步，都要能安全地重复执行。
重试、重跑和缺失数据，都要如实记录。
这里面哪一条，最让你头疼过？

上一期，我们设计了一个评测每个 pull request 的 GitHub App。
webhook 进来，存一个 run，sandbox 跑测试，
结果作为 check 回到 commit 上。
这是理想路径。这期讲的是其他所有情况。
先说一切的起点：webhook。
我们要在每个新 commit 上跑评测，所以得第一时间知道有新 commit。
webhook，就是 GitHub 主动通知我们的方式。
我们事先给 GitHub 登记一个网址，这就是 webhook 地址。
每次有人往 pull request 推 commit，GitHub 就往这个地址发一个请求，
里面写着是哪个仓库、哪个 pull request、哪个 commit。
问题是，这个地址是公开的，谁都能往里发请求。
所以收到请求，第一件事是校验 GitHub 的签名。
GitHub 会用一个只有我们双方知道的密钥，给每条消息签名。
我们用同一个密钥再算一遍，对得上，才往下处理。
但签名只能证明：这条消息确实来自 GitHub。
它不能证明，这个客户有权使用这个仓库。
这需要另一道检查：这个仓库的安装，是不是绑在这个客户的账号上。
GitHub 还可能把同一个事件发两次。
所以我们记下每个 delivery ID，重复的直接忽略，
把事件存好，马上回复。
下一个坑在安装流程里。
用户装完 app，GitHub 会把他跳回我们这里，
URL 里带着一个 installation ID。
很想直接信它，但 URL 谁都能改。
所以我们只把它当线索，不当证据。
整个流程绑定一个一次性链接，十分钟过期，
再由 GitHub 自己的授权来确认，
这个用户真的有这个安装的权限。
如果中途 app 被卸载，链接就直接失效。
接下来，要定义清楚，一次 run 到底是什么。
对我们来说，就是一个仓库、一个 pull request、一个 commit，
加上一个评测版本。
我们永远跑确切的 commit，不跑分支名，
因为测试跑着跑着，分支可能就动了，
结果描述的就是没人测过的代码。
来自 fork 的 pull request 直接跳过，
因为那是外部代码想跑在我们的机器上。
app 的私钥也永远不离开后端。
再说网络。消息会丢，也会迟到。
假设我们启动一次评测，响应丢了。
到底启动没有？直接重试的话，可能跑两遍。
所以先把 run 存下来，再带上幂等键发出去，
幂等键就是 run ID。
不管到达多少次，都只算一次评测。
迟到的消息是反过来的问题：
旧的尝试比新的晚结束，把新结果覆盖了。
所以每次更新都带一个 attempt ID，
和一个只增不减的序号，
比我们手上更旧的，一律忽略。
GitHub check 也带着 run ID，
所以我们是更新它，而不是再建一个重复的。
这就引出一个常被混淆的区别：重试和重跑。
重试，是重复一个基础设施步骤，
比如重发请求，或者重新发 check。
还是同一个 run，结果不变。
重跑，是把测试再执行一遍，那是一次新的测量。
所以我们保留第一次的结果，老老实实标注：
第一次就通过，还是重跑才通过。
第三次才过的测试，不叫可靠，叫不稳定。
如果是我们自己的基础设施出问题，
check 显示的是 action required，不是 failed，
也不计分。
我们宕机，不该怪你的代码。
然后是比较。
每个结果都要和基线比，
只有其他条件都一样，比较才公平：
测试版本、评测器版本、
模型设置，还有运行环境。
所以每个结果，我们都记下这套配置，
对不上就拒绝比较。
缺失数据也要小心。
零，是测了，失败了。
缺失，是根本没测。
把缺失当成零，平均分就会无缘无故往下掉。
所以缺失就是缺失，覆盖率单独报告。
还有几个小习惯，效果很大。
我们用 feature flag 上线。
关掉时，app 只响应健康检查。
打开了但配置不全，它直接拒绝启动，
而不是等到后面才出错。
三个密钥分开放：
私钥、OAuth 密钥，还有 webhook 密钥，
这样一个泄露，不会全线失守。
访问别的组织的 run，返回 not found，而不是 forbidden，
这样连它存不存在都不暴露。
同样的“只做一次”思路，也用在用量提醒上：
每个账号每周只提醒一次，不管多少个 worker 发现。
所以，如果你也要做类似的东西，记住四件事。
每个输入，先验证再信任。
每次 run，钉死在一个确切的 commit 上。
每一步，都要能安全重复。
重试、重跑和缺失数据，都要老实。

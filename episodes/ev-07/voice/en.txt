An eval case says "the agent should handle it well."
That case can't actually be graded.
What counts as "well"? A different grader, a different result.
Here's a common bad case. The input is one message:
"My headphones from last week broke, I want a refund."
It has three problems. Let's take them in turn.
The first problem is ambiguity. There's no order number,
so the agent could look it up or ask.
Both make sense; the task doesn't say which passes.
So a correct run might be marked as failing.
The second problem is that it can't be graded.
Who decides what handling it well means?
One reviewer passes it; another fails it.
Scores shift with the grader, so runs can't be compared.
Last, it can't be repeated, because order data changes.
It's refundable today, but past thirty days next month.
The task is unchanged, but the right answer changed,
so you can't tell if the agent changed or the data did.
So let's rewrite it and fix all three.
Pin the input: the same message plus the customer's account.
Pin the order data too: headphones bought ten days ago,
costing two hundred ninety-nine dollars, bought by this customer.
So any day it runs, it faces the same order.
For the ambiguous step, say both paths pass,
so neither gets marked wrong.
Finally, split "handles it well" into conditions you can check.
A two hundred ninety-nine dollar refund was issued, exactly once;
it looked up the order and checked ownership first;
and it emailed the customer a confirmation.
All three can be checked in the database and call log.
Each is yes or no, not anyone's gut feeling.
The task passes only if all three hold.
So to judge a task, ask three questions.
Would someone else read it the same way?
Can every condition actually be checked?
If you run it ten times, does each run start the same?
Three yeses, and it goes into the eval set.
Try having two colleagues grade it separately.
If they disagree, the task isn't clear yet.
In short, write success as conditions you can check.
